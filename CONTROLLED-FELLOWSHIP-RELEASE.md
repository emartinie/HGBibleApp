## Proposed release configuration

Committed `data/fellowship-testing.json` is **disabled**. The only supported mode is `readonly-fixtures`. A later owner-approved activation must specify `enabled:true`, UTC `startsAt` and `expiresAt`, with a window no longer than 24 hours. This task does not activate it. The hidden entry, after approval/publication, is `https://homegroups.org/?card=fellowship-test&week=12` (substitute the current study week). The old experimental `?card=fellowship` entry is also sent through this gate, never directly to live features.

Access requires the online flag, a valid active window, a restored non-anonymous account, an unexpired Firebase ID-token result with **boolean** `homegroupsOwner:true`, and an unchanged current UID. The claim matches the existing moderation owner's convention. No email/name/UID allowlist, URL parameter, profile field or browser-storage switch can grant entry. Initial/foreground/periodic checks refresh identity; account/token changes invalidate prior checks and remove the view. Expiry has its own teardown timer. No sign-in, linking, claim-setting or credential shortcut is present. An already existing owner claim must be verified by the administrator; if missing, access fails closed and separate trusted provisioning would be required.

Both `index.html` and the legacy `js/app.js` compatibility entry install the immutable production policy before the shared card runtime boots. There is no fallback to the unguarded component entry if the policy fails to load. The shared loader is moved, not rebuilt, into `js/card-app-runtime.js`. Loading/error text now uses DOM text rather than interpolating an untrusted card name into HTML; the production policy rejects invalid card identifiers. This closes a pre-existing route-name markup-injection risk. A unique runtime path avoids a previous service worker's cached app module. The controlled renderer must advertise its read-only capability version; an older/incompatible module is rejected before initialization.

## Exact public exposure and privacy limit

**GitHub Pages is static public hosting, not an owner-authenticated resource server.** Normal UI access is owner-gated, but anyone can download the new JavaScript, generic gate fragment, disabled flag JSON, read-only fixture module, CSS, tests and documentation. These contain only fictional samples, public feature settings and code—no token, secret, owner UID/email or real member/location dataset. Source restrictions can be bypassed by someone running arbitrary JavaScript in their own browser; they do not confer Firebase permissions. Firebase rules/IAM remain the resource authorization boundary.

If “administrator-only” means HTTP-level confidentiality of unfinished code or fixtures, this candidate **cannot satisfy that requirement on the existing Pages site**. It needs a separately approved authenticated server/edge or appropriate private hosting. Do not approve publication without explicitly accepting public synthetic assets with an owner-gated normal UI. No such infrastructure is created here. [GitHub documents the available private-site access controls and their enterprise prerequisites](https://docs.github.com/en/enterprise-cloud@latest/pages/getting-started-with-github-pages/changing-the-visibility-of-your-github-pages-site).

Neither historical GeoJSON file nor any real record/rule is modified. No historical URL is fetched by this test renderer. **The pre-existing datasets remain publicly reachable through their existing URLs and ordinary Prayer Map; this feature flag does not remediate that exposure.** Their approval-gated minimization/consent proposal remains [unchanged](tools/fellowship-preview/PRIVACY-PROPOSAL.md). No precise data is copied into the test fixtures. Existing standalone Commons URLs still exist outside test mode and retain normal Firebase authorization; this change does not globally disable existing production messaging.

## Rollback procedure (documented, not executed)

Prefer a **two-stage release**: first publish this disabled configuration after approval and smoke-test ordinary navigation; then approve a separate flag-only activation commit/window. This makes the normal rollback a small revert/disable of that activation, retaining the owner gate and all PR #31 security fixes.

- **First stop new testing access:** prepare an owner-approved commit setting `enabled:false` in the flag. Publishing that change to main is itself a deployment and needs authorization. Verify the served JSON and that a fresh/foreground test page is denied; close already open test tabs. No data undo is required because the test has no real writes.
- **If shell/navigation regress:** keep the flag off and prepare a narrow reviewed forward fix that retains the gate and PR #31 identity/privacy guards. Do not blindly revert the controlled commit: its parent PR #31 is an unflagged Fellowship implementation. Do not blindly revert the combined release either: that removes the hardening. A full last-known-good-main rollback is a last resort requiring explicit owner approval of these security effects and preservation of unrelated later work. Do not force-reset main. Any fix/revert merge also publishes.
- Verify the new Pages run and published assets, normal Prayer Map and study navigation, then refresh/reopen Safari and check the active worker/cache version. The prior worker's activation clears obsolete shell-cache versions; verify it rather than mass-clearing localStorage/IndexedDB or user data. A missing/offline flag fails closed even for a cached controlled shell.
- Rules, Firebase provider settings and production records are unchanged and must not be rolled back or edited as part of this frontend rollback. Historical public copies cannot be retracted by toggling a flag.
