# Commons Messaging Phase 2 plan

Planning only. No Phase 2 implementation, migration, Firebase configuration change, or deployment is authorized by this document.
Baseline audit: 36e3516 (November 4, 2026). Phase 1 review: PR #29, codex/commons-privacy-phase1.

## Entry gates

Complete the active-rules export/reconciliation and non-production authentication checks listed in SECURITY-PHASE-1.md. Confirm whether merging main publishes GitHub Pages. Keep deployment authorization separate. Do not expand community access until authorization, blocking and abuse handling have been reviewed and tested.

## Priorities and acceptance criteria

| Order | Priority | Work | Design constraints and acceptance evidence |
| --- | --- | --- | --- |
| 1 | P0 before community expansion | Blocking, DM reporting, abuse prevention and suspension | Define recipient preferences and block semantics first, including retained-history access. Enforce blocked invitations/sends on the trusted authorization path, not only the UI. Add a private, minimal report-evidence workflow with audited reviewer access; do not grant moderators blanket DM reads. Apply backend request/message quotas and abuse monitoring; App Check supplements authentication rather than replacing it. Test blocked sender/recipient, direct SDK bypass, revoked membership/roles, duplicate reports, mass requests, recovery and retention. Obtain separate approval for any backend/rules rollout. |
| 2 | P1 delivery correctness | Remove the first-100-message ceiling | Subscribe to the newest message page; render chronologically and page older history with stable server-time/document-ID cursors. Keep pending local writes distinct from server-confirmed messages. Preserve scroll position and avoid duplicates during live updates. Test 101, 1,000 and equal-timestamp messages, concurrent arrivals, reconnects and permission failures; newest messages must appear immediately and all authorized history must be reachable. No silent truncation. |
| 3 | P1 inbox completeness | Remove the 50-conversation ceiling and add correct activity ordering | Page an indexed, participant-scoped query ordered by trusted last activity and stable tie-breaker. Keep incoming pending requests independently reachable. Maintain last-activity summaries through a narrowly authorized transaction or trusted backend, with immutable participants/requester and validated summaries. Test more than 50/500 conversations, old threads receiving new messages, ties, deletions, pending requests and cross-account query denial. Never sort only a truncated client subset. |
| 4 | P1 request correctness | Idempotent invitation creation | Define canonical identity-pair handling and a rules-compatible create-or-resolve operation. A missing-document read currently cannot be assumed permitted; design the transaction/service and rules together. Simultaneous opposite-side requests, retries and repeat profile taps must resolve to one conversation without overwriting acceptance/decline. Test existing conversations outside the first inbox page, create races, timeouts and replay. Define cancellation and recovery policy before enabling new transitions. |
| 5 | P1 unread correctness | Private, cross-device unread state | Track latest incoming activity and a per-user read cursor using server-authoritative ordering. Advance only for messages actually displayed in a visible thread; a later outgoing message must not erase unread incoming activity. Protect markers from other users and constrain them to authorized conversations. Test own-message-after-unread, background tabs, pagination, reconnects, multi-device reads, concurrent arrivals and storage failures. Clearly distinguish unavailable counts from zero. |
| 6 | P1 identity clarity | Trustworthy request/peer labels | Replace unverified URL-name persistence with an authorized minimal identity source. Separate member-controlled display names from local aliases and never imply verified real-world identity. Preserve private profile/email restrictions and opt-out behavior. Test spoofed name links, undiscoverable members, account switches and multiple same-name contacts. |
| 7 | P1 navigation/offline correctness | Global messaging routes and service-worker navigation caching | Make DM access independent of weekly pilot limits. Preserve safe sign-in return destinations and request context. Correct the service worker so a successful account/DM navigation cannot overwrite the cached root shell. Define offline sending explicitly; never claim a queued write was cancelled merely because a page closed. Test direct signed-out links, all study weeks, back/forward, refresh, stale caches, offline root navigation and session transitions. |
| 8 | P2 usability and accessibility, before broad mobile rollout | Mobile navigation and transcript interaction | Use consistent Account/Return to study navigation, a distinct requests view, reliable loading/retry states and visible send status. Add transcript semantics and keyboard/focus management; preserve position when reading older messages. Test 320/390px widths, zoom, touch targets, soft keyboard/safe areas, screen readers and real Safari/iOS. Keep security errors distinct from empty inboxes. |
| 9 | P2 maintainability and scale | Notifications, query cost and operational diagnostics | Replace silent listener failures with bounded retry and privacy-preserving diagnostics. Avoid rebuilding every message listener on unrelated inbox changes and unbounded community N+1 scans. Define notification privacy, delivery expectations, retention and account deletion. Add query/index budgets, metrics and regression coverage before push notifications or attachments. |

## Implementation sequence

Agree on recipient/block policy and the conversation-summary/read-cursor schema first. Implement the abuse controls and authorization tests, then message pagination, indexed inbox/activity summaries, invitation idempotency and unread tracking. Ship each as a focused review branch with migration and rollback notes when applicable. Navigation/offline and accessibility work can be designed alongside these changes but must not weaken the same account/thread protections.

Every phase needs executable success and denial tests, two-account failure/retry scenarios, explicit loading/error behavior, and review of index/rules changes. Use synthetic records only in emulators or an explicitly authorized non-production project. Production migrations, emails, test messages, configuration changes and deployments require separate authorization.
