# Historical location exposure — correction proposal only

No original GeoJSON, Firebase record, rule or configuration is changed by this preview. No modified real dataset is published. Its single fictional map fixture is authored independently of historical records.

The #31 aggregate review found 2,000 coordinate pairs in each public historical GeoJSON copy, with 1,998 above two decimal places and no consent/opt-in property. This does not establish whether consent exists elsewhere. The map rounds displayed pins, but downloads the original file; Find Users also reads a historical source. Geometry, nested properties, descriptions and contact fields can disclose information even when the displayed pin or popup is masked. Existing prayer/feast listeners likewise receive raw document coordinates before rounding; production records and active rules have not been queried here.

## Proposed correction requiring separate approval

1. Inventory both `HomeGroupsMap.geojson` and `data/HomeGroupsMap.geojson`, all references, publicly readable Firestore location fields, repository history, caches and backups. Establish who owns the data and what publication purpose/consent was actually authorized. Do not infer location consent from account membership, a name-directory opt-in or a historic import.
2. Agree on eligible records and location granularity. Prefer voluntary city/region disclosure; two decimals is not anonymity, particularly in sparse areas. Records lacking verified publication consent should be excluded from a public output pending review, while the original is preserved in authorized restricted storage under an agreed retention policy.
3. Prepare an **unpublished dry run** of a minimal public GeoJSON. Keep only approved display labels and deliberately coarse coordinates needed by the current consumer. Round or remove every coordinate representation, including geometry and nested fields; omit raw addresses, contact details, identifying descriptions and unnecessary identifiers. Do not leave a precise original reachable through an alternate URL.
4. Validate counts/eligibility privately, scan for precision and identifying fields, and check existing map/directory behavior. Obtain approval for the exact output and the access/retention changes before replacing/removing any public source. Both current URLs, static copies and deployment packaging need coordinated treatment. A newly sanitized file does not fix an original that remains publicly downloadable.
5. For new publication, design a private auditable consent record (purpose, version, time, subject, permitted granularity and withdrawal) and trusted server validation/minimization. The current prayer checkbox and client rounding alone do not provide server enforcement or auditable historical consent. Any schema/rule change must be separately proposed and reconciled with authoritative production rules.
6. Document residual exposure: public Git history, prior browser/CDN/service-worker caches, backups and third-party copies may retain original coordinates. Removing a current URL cannot retract those copies; owner-approved retention/erasure and communication decisions are needed.

Approval must identify the data scope, eligibility/consent evidence, precision, fields, private retention location, publication/access changes and validation owner. This document does not authorize a migration, deletion, history rewrite, rules change or publication. Historical location privacy remains a release blocker. The safe visual preview avoids the exposure by serving synthetic data only.
